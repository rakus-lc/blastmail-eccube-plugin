# blastmail連携プラグイン（BlastmailSync）for EC-CUBE 4.3

> ⚠ **本プラグインは参考コードで、動作の保証はありません。** ご利用を検討される場合は、株式会社ラクスライトクラウドまでご相談ください。

EC-CUBE の会員を blastmail の読者へ同期し、blastmail 側で購買属性による絞り込み配信・ステップメールができるようにします。配信結果は EC-CUBE の管理画面から確認できます。

## できること

- 会員（本会員）を blastmail の読者へ一括同期（管理画面のボタン／`bin/console blastmail:sync`）
- 同期する項目を設定画面でマッピング（会員ID・氏名・会員登録日・購入回数・累計購入額・最終購入日・最終購入商品／カテゴリ など）
- 会員登録・編集・退会・削除に追従して即時反映（退会・削除は「配信停止」）
- 同期方式を選択: 全件（毎回すべて送る）／差分（変化した会員だけ送る。メールアドレス変更は読者 ID 指定で書き換え、対象外になった会員は配信停止）
- 配信状態（受信可否）の同期。EC-CUBE 側のオプトアウトを blastmail の「配信停止」へ反映しつつ、読者本人の「解除」「エラー停止」は上書きしない
- blastmail の直近の配信履歴と同期ログを管理画面に表示

## 使い方

1. blastmail 管理画面「読者項目の設定」で受け取りたい項目を作成する（項目名と入力タイプは下の「1 で作る読者項目の一覧」のとおり）
2. EC-CUBE 管理画面 会員管理 ＞ blastmail連携設定 で API 認証情報を登録し「接続テスト」
3. 同じ画面で EC-CUBE の値と blastmail の項目表示名を対応づけて保存（**「保存して項目名を自動で割り当てる」**で、同じ名前の項目は自動で入ります。後述）
4. 会員管理 ＞ blastmail連携 で「今すぐ同期」。定期実行は cron に `bin/console blastmail:sync`（`--full` で差分を無視して全件、`--dry-run` で CSV 確認、`--reset-state` で差分状態を破棄）

### 1 で作る読者項目の一覧

blastmail 側の「項目名」と「入力タイプ」（読者項目の設定画面の項目名そのまま）。必要なものだけ作ればよく、作らなかった項目はマッピングを空欄にします。

| 項目名 | 入力タイプ | 対応づける EC-CUBE の値 | 備考 |
|---|---|---|---|
| E-Mail | E-Mail入力 | メールアドレス | blastmail の既定項目（`c15` 固定）。新規作成は不要。**必須** |
| EC会員ID | テキストボックス | EC-CUBE 会員ID | 会員を特定するキー |
| 氏名 | テキストボックス | 氏名（姓 名） | 差し込み用。姓・名を分けたいときは「姓」「名」を別項目に |
| フリガナ | テキストボックス | フリガナ（セイ メイ） | |
| 会社名 | テキストボックス | 会社名 | |
| 都道府県 | テキストボックス | 都道府県 | 地域別の出し分け |
| 会員登録日 | 年月日入力 | 会員登録日 | |
| 保有ポイント | テキストボックス | 保有ポイント | |
| 購入回数 | テキストボックス | 購入回数 | キャンセル等を除く |
| 累計購入額 | テキストボックス | 累計購入額 | 税込・送料込の支払合計 |
| 最終購入日 | 年月日入力 | 最終購入日 | |
| 最終購入商品 | テキストボックス | 最終購入商品 | 直近受注の先頭商品名 |
| 最終購入カテゴリ | テキストボックス | 最終購入カテゴリ | 直近受注の先頭商品のカテゴリ名 |
| 状態 | （作らない） | （プラグインが管理） | 配信中／配信停止／解除／削除／エラー停止。状態変更 CSV でのみ送る予約列 |

- **項目名は blastmail 側の表示名と完全一致**させます。CSV のヘッダは defineID ではなく表示名で突合され、未知のヘッダが 1 つでもあると全行がエラーになります（プラグインは送信前に項目一覧と照合して未然に止めます）
- **金額・回数も「テキストボックス」で作ります**。blastmail の読者項目に数値型は作れません（画面にも登録 API にも無い）。そのため **累計購入額・購入回数を「◯以上」のような数値範囲で絞り込むことはできません**（数値範囲の条件は数値型の項目にしか出ません）。閾値でセグメントを切りたい場合は、階級をプルダウン項目として持たせるなど別の設計が要ります
- **年月日入力**は `yyyyMMdd`、または `yyyy/M/d`（本プラグインが送る `Y/m/d` はこの形）で受け付けます。**1910-01-01 〜 2037-12-31 の範囲外はその行がエラー**になります
- 電話番号入力（`00-0000-0000` 形式）・郵便番号入力（`000-0000` 形式）はハイフン必須で、合わない値は行エラーになります。EC-CUBE の電話番号はハイフン無しなので、マッピングするなら整形が要ります
- **空欄の列は「更新しない」**（必須項目なら行エラー）。空欄を送っても blastmail 側の既存の値は消えません。未購入会員の最終購入日のように「値が無い」ことを表したい列は、blastmail 側に前回の値が残ります

上記の入力タイプ・書式・空欄の扱いは、2026-09-24 に blastmail の実環境で確認した挙動です。

### 項目名の自動割り当て

設定画面の「項目マッピング」にある **「保存して項目名を自動で割り当てる」** で、blastmail から取得した項目一覧と上の表の項目名を突き合わせ、**空欄の欄だけ**を埋めます。入力済みの欄は上書きしません。

照合は 2 段階だけです。

1. 項目名の**完全一致**
2. **正規化して一致**: 全角英数・全角スペースを半角に、英字を小文字に、空白と記号（`-` `_` `・` `/` `()` など）を除いて比較。`ＥＣ会員ID` や `購入 回数` はこれで一致します

**言い換えの辞書は持ちません**。「累計購入額」と「累積購入額」のように語そのものが違うものは一致せず、「一致する項目が見つかりませんでした」と出るので手で入力してください。似た名前に勝手に同期して事故るより安全側に倒しています。正規化すると重複する項目が blastmail 側にある場合も、どちらとも決められないので割り当てません。

認証情報は環境変数 `BLASTMAIL_SYNC_USERNAME` / `BLASTMAIL_SYNC_PASSWORD` / `BLASTMAIL_SYNC_API_KEY` / `BLASTMAIL_SYNC_BASE_URL` でも渡せます（環境変数が優先）。

### 認証情報の保存

パスワードと API キーは、サーバー側の秘密値 `ECCUBE_AUTH_MAGIC`（.env／環境変数。DB には無い）から HKDF-SHA256 で派生した鍵を使い、libsodium の secretbox で暗号化して DB に保存します。DB ダンプだけが流出しても復号できません（サーバーの環境変数まで漏れた場合は防げません）。

- `ECCUBE_AUTH_MAGIC` が既定値や短い値のままだと設定画面に警告が出ます。十分に長いランダムな値にしてください
- `ECCUBE_AUTH_MAGIC` を変更すると復号できなくなります。その場合は設定画面でパスワードと API キーを再入力してください（エラーメッセージで案内します）
- DB に一切保存したくない場合は環境変数で渡してください

## いつ連携されるか

初期設定を終えただけでは何も送りません。契機は次の 3 つで、組み合わせて使います。

| 契機 | 何が起きるか | 備考 |
|---|---|---|
| **手動** | 会員管理 ＞ blastmail連携 の「今すぐ同期」（差分モードでは「全件を送り直す」も） | 初回の全件登録はこれか cron で行う。対象会員が 20,000 名を超えるとボタンは無効になり、コマンド実行を案内 |
| **定期（cron）** | サーバーの cron に `bin/console blastmail:sync` を登録 | プラグインも EC-CUBE 本体もスケジューラを持たないため、定期実行は cron 前提。差分モードなら毎回「変化した会員」と「状態を変える会員」だけ送る。**注文による購買属性の変化（累計購入額・最終購入日など）はここで拾う**（注文のたびの即時送信はしない） |
| **会員イベントで即時** | 下表の操作の直後に、その会員 1 名分を送る | 設定「会員イベントで即時反映」で ON/OFF（既定 ON）。API の失敗で EC-CUBE 側の処理は止めず、同期ログに記録して次回の定期実行で回収 |

即時反映の対象:

| EC-CUBE 側の操作 | blastmail 側の動作 |
|---|---|
| 会員本登録の完了（仮登録メールのリンクを踏んだ時点） | 読者を登録。受信可否が「受け取らない」なら配信停止に |
| マイページで会員情報を変更 | 属性を更新。受信可否が変わっていれば状態も変更 |
| 管理画面で会員を編集 | 同上 |
| 管理画面で会員ステータスを「退会」に変更 | 配信停止（EC-CUBE はこのときアドレスをダミーに置き換えるので、**前回同期したアドレス**で止める） |
| マイページから退会 | 配信停止 |
| 管理画面で会員を削除 | 配信停止 |

現実的な運用は「初回に手動で全件 → 以後は cron の日次差分を土台に、会員の登録・変更・退会はイベントで即時に追いつかせる」の組み合わせ。購買属性を送るなら cron は必須。

## 配信状態（オプトイン／オプトアウト）の同期

blastmail の状態: 配信中 / 配信停止 / 解除（読者本人の解除） / エラー停止 / 削除。

- **通常の同期 CSV に状態列は含めない。** blastmail は CSV にある列だけを更新するため、状態列を送らなければ読者の状態は変わらない。状態列を空欄で送ると「配信中」に戻ってしまうので、空欄では決して送らない
- **状態を変える必要がある会員だけ、メールアドレス列＋状態列の 2 列だけの CSV で別送する**
- EC-CUBE 発のオプトアウトは「配信停止」にマップし、読者本人の「解除」とは区別する
- 同期状態（`plg_blastmail_sync_state`）に、前回同期時の EC-CUBE 側受信可否（`opt_in`）と blastmail 側状態（`bm_status`）を持つ。**どちらが変わったかで新しい意思を決める**（意図マージ）
- 状態変更の送信に失敗した会員は、前回の値を保持して次回の同期で再送する
- **退会・同期対象外で配信停止にした会員が戻ってきたら、受信可否どおりの状態に戻す**。同期状態に「退会済み」の目印を残しておき、自分が送った「配信停止」を blastmail 側の意思として読み戻さない（読者本人の「解除」「エラー停止」は戻さず保護したまま）。退会中にメールアドレスが変わっていても、同じ読者のアドレスを書き換えるので読者は重複しない
- **上書きしなかったことは同期ログで確認できる**。全体同期では「本人が解除しているため配信を再開しなかった会員: N 名: アドレス…」（10 件まで列挙）、会員イベントの同期では「本人が解除しているため配信を再開しませんでした」と出る

方針は 3 つから選べる。設定画面に各方針の動作と、読者一覧取得の有無（性能）を明示している。

| 方針 | 新規登録 | 既存読者 | blastmail からの読者一覧取得 |
|---|---|---|---|
| **意図マージ・安全**（既定・推奨） | EC-CUBE の受信可否で登録 | 下の決定表。ただし**読者本人の「解除」は誰の操作でも上書きしない** | 同期ごとに配信停止・解除・エラー停止の一覧を取る |
| **意図マージ・あと勝ち** | EC-CUBE の受信可否で登録 | 下の決定表（「解除」も EC-CUBE 側の新しい操作で上書きする） | 同上 |
| blastmail を正 | blastmail 既定の「配信中」 | 状態は一切送らず、取り込みもしない | 取らない（大規模向け。EC-CUBE の「受け取らない」は blastmail に伝わらない） |
| EC-CUBE を正 | EC-CUBE の受信可否で登録 | 毎回 EC-CUBE の受信可否で上書き。**解除とエラー停止だけは上書きしない** | 同期ごとに取る |

決定表（意図マージ。`SyncService::decideStatus` に集約）:

| EC-CUBE の受信可否 | blastmail 側 | 動作 |
|---|---|---|
| 変わった | 前回から変わっていない | EC-CUBE の値を送る。「解除」の扱いは方針で分かれる（**安全**＝送らない。**あと勝ち**＝上書きして「配信中」に戻す） |
| 変わった | 前回から変わった | 順序が分からないので停止側を採る。blastmail が解除・配信停止なら EC-CUBE を「受け取らない」に取り込む。EC-CUBE がオプトアウトで blastmail が配信中なら「配信停止」を送る |
| 変わっていない | 解除・配信停止 | 送らない。EC-CUBE を「受け取らない」に取り込む（双方向オプトアウトが有効なとき） |
| 変わっていない | 配信中 | 触らない |
| 初回で「受信しない」 | 配信中 | 「配信停止」を送る |
| どれでも | エラー停止 | 送らない（宛先の事実。意思では覆らない。エラー停止連携を参照） |
| どれでも | 解除（**安全**のとき） | 送らない。双方向オプトアウトが有効なら EC-CUBE 側を「受け取らない」に揃える |

双方向オプトアウト（既定 有効）: 上の表の「取り込む」を行うかどうか。読者一覧は状態ごとに取得元が違う（**「解除」「削除」は `contact/trash/export`、「配信停止」「エラー停止」は `contact/list/export`**。解除・削除を list/export に投げると HTTP 400 になる。2026-09-24 実機で確認）。外すと blastmail 側の解除は EC-CUBE に戻らない。「配信中」は EC-CUBE に戻さない（同意は本人が EC-CUBE 側で表明したものだけを使う）。取り込みは会員イベントの即時同期でも全体同期でも行う。

### 受信可否（オプトイン）の項目

**標準の EC-CUBE 4.3 には、会員ごとのメール受信可否を持つ仕組みがない。** 会員テーブルにもメルマガ関連の列は無く、会員登録フォームにも同意欄が無い（規約同意はあるが配信同意ではない）。

そこで本プラグインが会員に「メールマガジンを受け取る」を追加する。表示・保存する場所は次の 3 か所。

- 会員登録フォーム（新規は未チェック。明示的に同意を取る）
- マイページ ＞ 会員情報編集
- 管理画面 ＞ 会員編集

描画はテンプレートを書き換えず、EC-CUBE の `eccube_form_options.auto_render` に任せている（コア側のテンプレートが拡張項目を自動で出力する仕組み。公式のメルマガ管理プラグインと同じ方式なので、テーマを差し替えても壊れない）。

公式のメルマガ管理プラグイン（[EC-CUBE/mail-magazine-plugin](https://github.com/EC-CUBE/mail-magazine-plugin)）が入っている場合は、そちらの項目（`getMailmagaFlg()`）を優先し、本プラグインは項目を追加しない。どちらも無い場合は本会員をすべて「受信する」として扱う。

## エラー停止連携（宛先不明の共有。blastengine 連携プラグインと組で使う）

**既定は無効**。設定画面「同期の対象と動作」の「エラー停止連携」で有効にする。会員の宛先状態の列は blastengine 連携プラグイン（BlastengineMailer）が持つので、そちらが有効でスキーマ更新済みのときだけ動く（列が無ければ何もしない）。

- **取り込み**: 同期の最初に blastmail の「エラー停止」読者一覧（`contact/list/export?status=エラー停止`）を取り、同じアドレスの会員を宛先不明（判定元 blastmail）にする
- **送る状態の優先順位**: 宛先不明の会員は、受信可否（オプトイン／アウト）に関係なく **「エラー停止」** を送る。blastmail 側が既に「エラー停止」「解除」なら送らない。通常の読者 CSV には状態列を含めない方針は変わらない（状態変更 CSV で送る）
- **アドレス変更**: 旧アドレスがエラー停止だった読者は、新アドレスに書き換えたうえで受信可否どおりの状態（配信中／配信停止）に戻す。新アドレスは未検証なので引き継がない
- 同期ログに「blastmail のエラー停止 N 件を取り込み、会員 M 名を宛先不明にした」「宛先不明のため『エラー停止』として送った会員: K 名」と出る

## 会員登録時の同意

会員登録フォームの受信可否は新規登録時に**未チェック**から始める（事前チェックによる同意は取らない）。EC-CUBE の仮登録→本登録のメール確認を経てから同期するので、アドレスの実在確認まで済んだ同意になる。

## 双方向オプトアウト（blastmail 側の解除・配信停止を EC-CUBE に戻す）

**既定は有効**（設定「同期の対象と動作」で切れる）。EC-CUBE → blastmail は従来どおり（「受け取らない」→ 配信停止）。加えて同期の最初に、blastmail 側で「解除」（配信解除リンクから本人が解除）と「配信停止」の読者を取り、同じアドレスの本会員の受信可否を「受け取らない」に更新する。差分状態の opt_in も false にするので、その会員に「配信停止」を送り直すことはない。

- 「配信中」は EC-CUBE に戻さない。同意は本人が EC-CUBE 側（登録・マイページ）で表明したものだけを使う
- **「解除」を覆せるかどうかは方針で決まる**（2026-09-24 決定）
  - **意図マージ・安全**（既定）: 覆さない。会員がマイページで「受け取る」に戻しても、運営者が管理画面で戻しても、blastmail の解除はそのまま。次回同期で EC-CUBE 側も「受け取らない」に揃う。再開するには読者本人に blastmail 側で登録し直してもらう
  - **意図マージ・あと勝ち**: 覆せる。ただし**管理画面の会員編集で「受け取らない → 受け取る」に変えたときは、保存時に確認ダイアログ**が出る（その会員が blastmail 側で解除している場合のみ。API から状態を取れなかったときは止めない）。上書きした事実は同期ログに残る
  - どちらでも**エラー停止は常に保護**し、EC-CUBE 発の「配信停止」は上書きできる
- 取り込みが起きるのは **EC-CUBE 側から取りに行ったとき**だけ（blastmail からの通知は受けていない）。契機は次の 2 つ
  - **全体同期（手動の「今すぐ同期」／cron の `blastmail:sync`）**: 同期の最初に「解除」「配信停止」の読者一覧を取り、同じアドレスの会員を「受け取らない」にする。差分モードでもこの突き合わせは対象会員すべてに対して毎回行う
  - **会員イベントの即時同期**（会員本登録の完了・会員編集・マイページでの変更）: その会員 1 名の現在の状態を取り、解除・配信停止なら取り込む
  - したがって**解除リンクを押した瞬間には EC-CUBE 側は何も変わらない**。反映は次の同期（実運用では cron の間隔ぶん遅れる）か、その会員にイベントが起きたときになる
- 受信可否の列は、公式メルマガ管理プラグインがあれば `mailmaga_flg`、無ければ本プラグインの `blastmail_opt_in`


## 高度な設定

- **会員イベントの反映方法**（既定: 応答後）: 会員の登録・編集などの直後に送る 1 名分の同期を、画面の応答を返した後に実行する。blastmail の API が遅いときでも管理画面・マイページの保存が待たされない（PHP-FPM 構成で効果がある。それ以外では体感が変わらないことがある）。「画面の処理と同時に送る」も選べる。どちらでも失敗はログに残り、次回の定期同期で回収される
- **同時実行ロック**（既定: DB）: 同期の二重実行を防ぐ方法。既定は DB のアドバイザリロックで、**同じ DB を見ていれば Web・cron が複数サーバーに分かれていても効く**。接続が切れれば自動で解放される。単一サーバーならファイル（flock）も選べる。SQLite などアドバイザリロックの無い DB では自動でファイルに切り替わる

## 制限事項

- **最終購入日・最終購入商品・最終購入カテゴリは、値が無くなっても blastmail 側から消えません。** blastmail は CSV にある列のうち**空欄の列を更新しない**ためです。全部の注文がキャンセル・返品になって集計対象が 0 件になった会員では、blastmail 側に前回の値が残ります（購入回数・累計購入額は 0 が入るので正しく更新されます）。消したい場合は blastmail 側で直接編集してください
- **金額・回数は数値範囲で絞り込めません。** blastmail の読者項目に数値型が無いためテキストボックスで持ちます（詳しくは「1 で作る読者項目の一覧」）
- 集計から除くのはキャンセル・購入処理中・対応中・返品の受注です

## 設計上の判断

- 送信前に blastmail の項目一覧と照合し、存在しない項目名があれば送らない（blastmail は未知ヘッダが 1 つでもあると全行エラーになる）
- インポート処理中（アカウント単位の排他）の応答には待って再試行する
- 独自項目を API で自動作成しない。blastmail 側で作った既存項目にマッピングする
- API 障害が EC-CUBE の会員登録・退会処理を止めないよう、イベント連携の例外はログに記録して握る

## 大規模（数十万〜数百万会員）での運用

- 会員は 1,000 件ずつ読み込んで都度メモリを解放し、CSV は「1 回に送る最大行数」（既定 50,000 行）で分割して順に送ります。会員数が増えてもメモリ使用量は増えません
- 対象会員が 20,000 名を超えると管理画面のボタンは無効になり、`bin/console blastmail:sync` の実行を案内します。進捗（走査数・送信済み行数）は管理画面に表示され、5 秒ごとに自動更新されます
- 同時実行はファイルロックで防ぎます（2 本目は「別の同期が実行中」で終了）
- 初回の全件は blastmail 側の取り込み時間が支配的です（200 万会員で 30 分程度の見込み）。差分モードなら 2 回目以降は変化した会員だけになります

## blastmail API を叩くうえでの注意（実測で判明）

- レスポンス形式の指定は **`f=json`** を使う。`format=json` を GET に付けると実環境で `illegal format: json,json`（HTTP 500）になる（2026-09-04 api.bme.jp で確認）。念のため XML が返っても読めるようにしてある
- 環境変数は `$_ENV` / `$_SERVER` / `getenv()` の順に見る。Symfony の Dotenv は既定で `putenv()` を呼ばないため、`.env` に書いた値は `getenv()` だけでは取れない

## 動作環境

EC-CUBE 4.3 系（PHP 8.1 以上）。blastmail 外部公開 API（HTTPS, `https://api.bme.jp/rest/1.0`）を利用します。
